# Local operation and recovery

The browser editor at `/app/` reuses the shared Ablo login. Signed-out browser users can open the ordinary shared Google/email sign-in page; Forum resumes once that cookie is available. Browser **Sign out** revokes the shared browser session across Ablo products. Membership revocation still invalidates access within the bounded lease.

The updated native screen offers **Continue with Google** and **Continue with email**. Google opens the system browser and returns through the registered Forum protocol with S256 PKCE; email accepts a six-digit issuer code. These flows require Forum's exact frontend origin and callback scheme in hosted Auth's trusted list. Older downloads can still use the earlier device flow until replaced. The native process encrypts sessions using the OS keychain; a failed or unavailable keychain never causes plaintext token storage. Session expiry or removed membership returns to sign-in. Network failures retain drafts; account authorization is required before opening them again.

For local development, prepare a separate Ablo project using the README commands and keep `.env.local` private. `ABLO_API_KEY` selects explicit project mode. Hosted Ablo owns documents, steps, chat and receipts; the app provides no local backend emulator. Expired branch credentials require the normal Ablo CLI renewal. Temporary hosted test branches expire within 24 hours and must never hold persistent user documents.

Electron stores pending edits under the OS user’s Forum application-data directory. `LOBBY_DOCS_PROFILE` selects an isolated directory. Hosted draft files are bound to endpoint, organization and user; development drafts use the service-returned project and branch. Sign-out closes the active database and hides its records without deleting pending edits. The next authorized sign-in to the same account recovers them. Do not share a profile between unrelated OS users or bypass the single-instance lock.

Edits save locally before transmission. Network interruption preserves pending steps. Keep the window open after a local save failure and resolve filesystem/disk problems. Switching documents saves pending steps locally and restores them when you return. Reopening recovers the first independent draft; additional windows recover additional drafts. Old local-only databases are preserved but are not imported into Ablo automatically.

Close the app before backing up the complete profile. Retain SQLite WAL/SHM files if present. Restore into a separate profile first and verify pending-edit recovery. This backs up local drafts; back up authoritative project data using your Ablo development service’s facilities. Filesystem permissions protect local data; draft files are not application-encrypted. Never commit profiles, databases, credentials or recordings.

The optional agent executable is trusted operator-installed software. Use a dedicated profile. The app does not provision model access. Catalog failure blocks agent requests. Stop retains accepted changes. Interrupted runs expire instead of automatically replaying potentially destructive instructions.

`npm run test:integration` and `npm run test:electron` create synthetic records in the configured development branch. Use a disposable branch with no private documents when recording a demo. `npm run test:auth` and `npm run test:browser` use explicitly simulated services to verify account boundaries and recovery. `npm run make` creates the current Mac package. Optional signing and notarization use an installed Developer ID identity and a keychain profile; no Apple secrets belong in configuration or source. Verify the extracted distributable with codesign, Gatekeeper and stapler, then verify the real hosted handoff and restart before publishing a download. Do not publish a Google/email build before the matching Auth registration is released.

Keep automated chat and editing checks in a disposable development branch or the explicit in-memory fixtures. Production release checks should reuse an authorized session and read existing data; do not post connection-check messages into a user's workspace. If a live mutation is explicitly needed, label its disposable document, record its exact IDs and remove only that test data afterward.

For a disposable verification run without application database setup, Ablo supports explicitly hosted **test** branches with an expiry within 24 hours. Use the CLI’s `branch ensure --kind test --hosted --expires-at ISO_TIMESTAMP` workflow, then push this schema using that branch’s key. Such branches are temporary test data, never a persistent document workspace. An ordinary development project needs its persistent data plane configured separately on hosted Ablo.

The hosted agent loop supports `anthropic` and `gateway` provider configurations described in the architecture document. For real model verification, export the provider configuration, the disposable branch key as `ABLO_API_KEY`, its exact `FORUM_LIVE_TEST_BRANCH` ID, and a private `FORUM_AGENT_TRACE_DIR`; run `npm run test:agents:live`. This check writes synthetic documents in that branch. It records fixture-only model inputs, tool calls/results and measured provider usage for inspection outside Git. A provider 401 indicates rejected credentials; a gateway 402 indicates a billing or credit block. Neither is a reason to substitute another credential silently. Restore the approved connection or balance, then rerun the explicit live check. Provider failures are recorded with model, error name and HTTP status in the private trace; raw headers and provider error bodies are excluded. The browser agent check `npm run test:agents:browser` uses explicitly simulated identity, model and storage.
